# Security and safety

Single user, but it holds a CV, contact details, job history and Gmail-derived data, and the code is public. Treat it like a real product.

## Assets
CV and profile facts; job/application history; alert-email content; API keys (Anthropic, Reed, Adzuna, HMAC secret); Firebase project; the user's Google account.

## Threats → controls
| Threat | Control |
|---|---|
| Secret leaked via public repo | Secret Manager for all keys; `.env*` gitignored; gitleaks pre-commit (fail-closed: no gitleaks, no commit) + CI over full history; GitHub secret scanning + push protection on; rotate any key that ever touches a commit |
| Personal data in repo | Fixtures are fake; `evals/` holds fake postings judged against a fake candidate (the fake CV's facts, invented work rights), so its recorded model answers contain no personal data (ADR-036); CV never committed (`.gitignore` blocks `.docx`/`.pdf`/`.jsonl` outside fixtures and evals); docs describe the user generically and candidate-specific values (e.g. `{profile.work_rights}`) are templated from the Firebase profile at runtime; `npm run scan:pii` (in `check` and CI) fails on non-allowlisted emails/phone numbers in tracked files. History was rewritten once to remove personal details (ADR-010) |
| Someone else reads the data | Firestore/Storage rules: `request.auth.uid == config/app.ownerUid` on every path, default deny, fail-closed until `config/app` exists; `config/*` never client-writable, so ownership can't be claimed; rules unit-tested for every collection (ADR-011); the only client writes are owner fact edits with versioned snapshots (including an optional https-only `evidenceUrl`, ADR-024), criteria versions (including optional lane points, ADR-034), the owner's work-rights setting on `profile/main` (exact keys, enum, server time, ADR-033), job actions (status, applied stamps and 👍/👎 on `jobs`, nothing the funnel writes) with create-only `events` (M5, ADR-038), CV uploads (PDF/DOCX ≤ 5 MiB, immutable) and marking an upload removed (`removedAt` only, once, ADR-023), each tested for owner allow, anon deny and other-user deny (ADR-018, ADR-019); callables re-check the owner UID with the Admin SDK; App Check (reCAPTCHA Enterprise) enforced on Firestore, Storage, callables; new sign-ups and client-side account deletion disabled after bootstrap (Authentication → User actions, ADR-015) |
| Forged calls to webhooks | `ingestEmailJobs` (M6, ADR-046): HMAC-SHA256 with the shared secret over `v1.<timestamp>.<nonce>.<raw body>` (so the body, the time and the nonce are all covered), verified on the raw bytes before anything else; reject if the timestamp is more than 5 min from the server's clock, or if the nonce was used (`nonces/{nonce}` created with `create()`, kept 10 min, at least twice the skew, so a replay is always caught; TTL policy deletes them); the nonce is written only for a request whose signature verified; constant-time compare (`crypto.timingSafeEqual`) after a length check, with the same 401 for every signature, skew, header or replay failure and no body echoed or logged; both sides trim the secret. The function is publicly invocable (Apps Script can't present a Google identity or an App Check token), so the HMAC is the authentication; one instance at most |
| Fetching a site we must not (M6, ADR-049) | LinkedIn, Indeed, Wellfound and Glassdoor are never requested (CLAUDE.md hard rule, ADR-004): `createHttpClient` takes `forbiddenHosts` and `scanHttpClient` always passes `FORBIDDEN_FETCH_HOSTS`, so a request to those hosts or a subdomain throws `forbidden_host` before any fetch, robots.txt included (tested with a `fetch` spy). The list is also the default for any client, and redirects are followed by hand, 3 hops at most, each checked against it. Lookup reads job-board URLs only from the four official board APIs; any other pasted URL is never fetched. A pasted results page is text and anchors only: the browser parses it with `DOMParser` and sends back `{href, text}` strings, never inserting it into the page; the server takes a LinkedIn ID only from an anchor, never from model text. |
| Prompt injection in job posts / emails | Alert emails are untrusted data (M6, ADR-047): LinkedIn alerts are parsed by deterministic code with no model; for other senders one cheap-model call has no tools, a fixed schema `{ jobs: [{ title, company, location, linkIndex | null }] }` and the email in an `<email>` tag it can't close, and the model can't plant a URL because links are read from the HTML in code and the model returns an index into the numbered list (out of range → dropped); a link off the host allowlist is stored on the source ref only, marked unverified, giving no keys and never followed or logged; an injected title stays text in the title and goes through the funnel like any posting. Funnel LLM calls have no tools and fixed schemas; every job-derived field (title and company included) is wrapped in a `<job_posting>` tag the text can't close, with explicit "data, not instructions"; outputs can only write verdict fields on that job, through a store that validates each patch against an allow-list of funnel fields and has no method for criteria, profile or config; fit, luck and the verdict are computed in code, and a requirement counts as met only if it cites a real profile fact (ADR-034); the eval set has five injection cases that must all come out right (ADR-036). The profile calls (`parseCv`, `addFact`) follow the same pattern: tagged input that can't close its own tag, fixed schema, output validated with zod and evidence checked against the source text (ADR-018). Evidence links are not in the model's output schema, so injected text can't plant a link (ADR-024) |
| Hallucinated CV content | CV bullets must cite `factId`s; validator rejects unreferenced claims; user reviews before download |
| Runaway cost (loop, bug, big run) | App-level spend cap in `llm.call()`: each call reserves its worst case in a transaction before it runs, so concurrent calls can't overshoot, every send has a hard time limit, and a call that never settles (killed at the callable timeout) is charged its worst case rather than dropped (ADR-016); per-run leases (M4, ADR-032): each scan or re-score reserves its budget once and every call reserves its worst case against it, so a run can't spend more than its lease, deep reads pause from 90% of the monthly cap, and a crashed run's lease is charged in full; max 1 function instance + single-flight lock; App Check tokens are consumed on calls that spend money; clients never auto-retry them; Anthropic console monthly limit; GCP budget alerts |
| Getting blocked / ToS breach at sources | Only public/official endpoints; robots.txt respected for web pages and unkeyed endpoints (Crawl-delay honoured), keyed official APIs (Reed, Adzuna) kept inside their developer terms and quotas (ADR-025); ToS checked before adding a source (ADR-026–028); `HireframeBot` User-Agent; per-host rate limit (≤ 1 req/s), at most 3 attempts with backoff on 429/5xx; no logged-in scraping |
| Gmail over-access | Apps Script runs in the user's own account with the Advanced Gmail service and the narrow `gmail.modify` scope (read and relabel; `GmailApp` would need the full `mail.google.com` scope), plus `script.external_request` and `script.scriptapp`; no `MailApp` scope until M7. It lists only `hireframe/alerts` messages, sends only `{ id, receivedAt, from, text, html }` (never a subject, To, Cc, Delivered-To or other header) to the signed endpoint, and relabels only on a per-message success. The digest (M7) sends only to the user's own address. `X-Forwarded-For` is never sent (it would hold the second account's address) |
| Data loss | Weekly JSON backup to Storage (8 kept); Firestore PITR optional; events are append-only |
| Account takeover | Google account 2FA (user); owner-only auth; no password auth enabled; sign-ups disabled |
| Dependency supply chain | Dependabot; `npm audit` in CI (production dependencies fail on high, dev-only tools on critical, ADR-013 addendum M3); lockfile committed; pinned GitHub Actions by SHA; deploys use keyless Workload Identity Federation limited to this repo, `v*` tags and the approved `production` environment (ADR-014) |
| Sensitive data in logs | Functions logger takes fixed event names and scalar fields only; the source HTTP client logs a host and a fixed label, never a URL (Adzuna's key travels in the query string), and scans log counts, never job text; redacts emails/phones and truncates strings; errors are logged by class and code, never message (zod issues and SDK errors can echo input); third-party console output is off (Anthropic SDK `logLevel: 'off'`, which `ANTHROPIC_LOG` can't override; pdf.js `verbosity: 0`); tests assert fixture CV text never reaches the log or the console on success and on every failure path (model timeout/abort, unusable output, extraction and store errors). Never log full descriptions or CV text |

## Data retention
- `skip` job descriptions purged after 60 days (metadata kept for metrics).
- Generated CVs kept until user deletes.
- "Delete all my data" admin action wipes collections + Storage. For the profile this is **Reset profile** (M2.1, ADR-023): an owner-only callable, confirmed by typing RESET, that hard-deletes every fact, version, upload document and uploaded CV file. Jobs, generated CVs and events join the wipe when they exist. **Deferred to M8 (decided in the M3 review):** M3 stores `jobs` (with descriptions), `runs`, `sources` and `companies`, and nothing deletes them yet. They are public postings and scan records, not CV or profile data, and Reset profile still clears all profile data. M8's retention job adds the wipe for them, which also meets Adzuna's terms (remove data acquired from Adzuna when the API account ends, ADR-025).
- "Remove upload" only archives (reversible); the uploaded file is kept until Reset profile.
